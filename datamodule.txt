DATA INGESTION AND STANDARDIZATION STRATEGY

1. MODULE OBJECTIVE
The primary goal of the initial data ingestion step is to act as a
universal translator. It reads raw clinical recording files from various
sources and converts them into a standardized HDF5 format. Crucially,
this step involves zero preprocessing; it is a direct, lossless
conversion of the original numerical data, timestamps, and annotations.

2. LONG-TERM BENEFITS OF EARLY STANDARDIZATION
Converting multiple file formats to HDF5 without any processing provides
immediate structural benefits that make downstream tasks significantly
easier, regardless of the data's origin. It is my opinion that this
approach prevents technical debt because:
- Unified Interface: Downstream users and scripts (whether for plotting,
  filtering, or machine learning) only need to know how to interact with
  one file type (HDF5) rather than navigating the specific quirks of
  EDF, EDF+C, or BIDS structures.
- Memory Efficiency: HDF5 allows users to retrieve specific channels or
  time segments instantly without loading entire massive files into the
  system's memory, which is a major limitation of standard continuous
  formats.
- Universal Compatibility: HDF5 is natively supported across numerous
  programming languages and analysis tools, allowing the entire
  laboratory to use the data without specialized translation scripts.

3. ARCHITECTURE AND EXTENSIBILITY
The ingestion module will be designed to avoid convoluted code by
strictly separating format-specific logic.
- Central Dispatcher: A central routing function will look at the
  incoming file extension.
- Independent Readers: It will pass the file to an isolated reading
  function built specifically for that format.
Because these reading functions do not interact with one another, adding
new data formats in the future simply requires writing one new isolated
function and updating the central dispatcher, leaving the rest of the
pipeline untouched.

4. CURRENTLY SUPPORTED FORMATS AND HANDLING RULES
- EDF+C (Continuous): The continuous numerical array, annotations, and
  metadata are extracted and saved directly into the HDF5 structure.
- BIDS Data (.eeg / BrainVision): The pipeline reads the three
  associated files (the raw data, the header, and the marker files) and
  consolidates them into the single HDF5 container.
- EDF+D (Discontinuous): To avoid wasting memory and creating artificial
  data, discontinuous files will not be zero-padded. Instead, the
  reading function will treat gaps as hard boundaries. Each continuous
  segment of the recording will be saved as an independent array within
  the single HDF5 file (e.g., segment_1, segment_2), alongside their
  precise starting timestamps. This perfectly preserves the original
  data without introducing massive empty arrays.

5. OUTPUT STRUCTURE AND THE GUARANTEE IT CARRIES
Every reader produces the same eight pieces of information, so the HDF5
output is structurally identical regardless of which format it came from:

    /                      attrs: schema_version
    /signals               attrs: discontinuous, n_segments
        data               (n_channels, n_samples)      continuous
        segment_0 .. N     one dataset each             discontinuous
    /channels
        names              one entry per channel
        units              one entry per channel
        sampling_rates     one entry per channel
    /events
        onsets, durations, descriptions
    /metadata              attrs: start_datetime, subject_id, equipment,
                                  source_format, source_file

Four input formats therefore produce two output shapes, and the branch is
not by format but by whether the recording has gaps. EDF, EDF+C and
BrainVision are continuous; EDF+D is discontinuous. The
/signals attribute "discontinuous" states which shape a file uses.

Channels are identified by position, not by label. Row i of
/signals/data is the channel named in /channels/names[i], carrying
/channels/units[i] at /channels/sampling_rates[i]. This mirrors EDF's own
convention, where the header lists signals in order and every data
record holds channel blocks in that same order.

THE GUARANTEE: a uniform-rate recording stores its signals as a single
rectangular dataset at /signals/data, with row i corresponding to
/channels/names[i]. Support for mixed per-channel sampling rates may add
further modes, but it will not change this layout. Downstream code
written against the rectangular form stays valid.

This matters because a rectangular array cannot hold channels sampled at
different rates — over thirty seconds, a 100 Hz channel needs three
thousand samples and a 1 Hz channel needs thirty. Supporting such files
requires a second storage mode rather than a modification of this one,
and downstream code will have to handle or refuse that mode explicitly,
exactly as it already must for discontinuous recordings.

6. SCHEMA VERSIONING RULE
The point of converting recordings is that the converted files outlive
the code that wrote them. A file converted today must still open years
from now, which places a constraint on how the schema may change.

The loader compares only the major part of the version. A file written
under schema 1.0 therefore opens under a 1.1 loader, and vice versa.

This is only safe if minor versions are additive. The rule:

- A minor increment may ADD a group, dataset or attribute. An older
  loader ignores what it does not recognise, and a newer loader must
  cope with the field being absent from older files.
- Anything that REMOVES a field, renames one, or changes the meaning or
  shape of an existing one requires a major increment. That is the only
  circumstance under which previously converted files stop being
  readable, and it should be treated as a migration rather than a
  version bump.

Matching versions exactly would be simpler to implement and much worse
in practice: every schema change, however small, would orphan every file
already converted, and the archive would only be readable by pinning the
release that wrote it.


FUTURE INTEGRATION STRATEGY: SPIKE2 (.SMR / .SMRX) DATA

1. CURRENT STATUS
Support for Cambridge Electronic Design (CED) Spike2 (.smr / .smrx)
recordings is intentionally deferred to prioritize the stability of the
core pipeline for standard recording formats (EDF, EDF+C, EDF+D, and
BrainVision).

2. ARCHITECTURAL SAFETY
Deferring this format carries zero risk of breaking the codebase in the
future. Because the ingestion module uses an isolated reader structure,
adding Spike2 support later will only require adding an independent
reader function to the system, leaving the existing pipeline completely
unaffected.

3. IMPLEMENTATION PATHWAYS (FOR FUTURE PHASE)

- Pathway 1: Native Library Integration
  Once modern compatibility is independently verified, implement a
  dedicated reader using official CED libraries (such as sonpy) or
  open-source packages (such as neo). This reader will extract
  continuous signals (such as local field potentials) and discrete event
  timestamps into their respective standardized sections within the
  single HDF5 container.

- Pathway 2: MATLAB Export Workaround (Primary Fallback)
  If direct library integration encounters dependency or compatibility
  conflicts, establish a lab protocol where Spike2 files are exported
  from the native recording software as MATLAB files (.mat). The
  ingestion module will contain a standard reader for MATLAB files,
  which avoids legacy dependency conflicts and integrates smoothly with
  modern computing environments.

- Pathway 3: Isolated Subprocess Execution (Secondary Fallback)
  If native software access is unavailable and legacy dependencies are
  required, execute the conversion through an isolated background
  environment. A minimal conversion script will run in the background
  to convert the file to HDF5 and return the clean data directly to
  the main pipeline.
